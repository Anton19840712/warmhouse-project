### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удаленно включать и выключать отопление в своих домах через веб-интерфейс
- Система поддерживает управление состоянием датчиков отопления (active/inactive)
- Пользователи могут обновлять целевую температуру для системы отопления
- Система отслеживает текущее состояние всех датчиков отопления

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в различных помещениях дома
- Система получает данные о температуре с датчиков, установленных в разных локациях (Living Room, Bedroom, Kitchen и т.д.)
- Система хранит историю показаний температуры для каждого датчика
- Пользователи могут просматривать информацию о каждом датчике (название, тип, локация, единицы измерения, статус)
- Система поддерживает запросы температуры как по локации, так и по идентификатору датчика

### 2. Анализ архитектуры монолитного приложения

**Язык программирования:** Go (Golang)

**База данных:** PostgreSQL

**Архитектурный стиль:** Монолитная архитектура

**Основные характеристики:**

- **Единая кодовая база:** Вся бизнес-логика (обработка HTTP-запросов, работа с датчиками, работа с БД) находится в одном приложении
- **Синхронное взаимодействие:** Все запросы обрабатываются последовательно, нет асинхронных операций или событийно-ориентированного подхода
- **Прямое взаимодействие с датчиками:** Сервер напрямую запрашивает данные у Temperature API (эмуляция физических датчиков)
- **Единая база данных:** Все данные (информация о датчиках, показания температуры, устройства) хранятся в одной PostgreSQL базе данных
- **Развертывание:** Требуется остановка и перезапуск всего приложения для внесения любых изменений
- **Масштабирование:** Возможно только вертикальное масштабирование (увеличение ресурсов сервера), горизонтальное масштабирование затруднено
- **Технологический стек:** Golang + PostgreSQL + Docker + HTTP REST API
- **Структура кода:**
  - `main.go` - точка входа, инициализация сервера
  - `handlers/` - HTTP обработчики запросов (sensors.go, devices.go)
  - `services/` - бизнес-логика и интеграции (temperature_service.go, device_service.go, telemetry_service.go)
  - `models/` - модели данных

### 3. Определение доменов и границы контекстов

После анализа приложения я выделил три основных домена:

**1. Управление датчиками**

Этот домен отвечает за работу с самими датчиками - их регистрацию, хранение информации о них (название, где установлен, какой тип, единицы измерения). Здесь же управляется статус датчиков - работает он или нет. Основная сущность - Sensor.

**2. Телеметрия**

Здесь собираются и хранятся все показания с датчиков. Система получает данные о температуре, сохраняет их с временной меткой, может посчитать статистику. Основная сущность - TelemetryReading.

**3. Управление устройствами**

Этот домен нужен для работы с умными устройствами в доме - отоплением, освещением и т.д. Можно регистрировать устройства, отправлять им команды (включить/выключить), смотреть их состояние. Основные сущности - Device и DeviceCommand.

**Как домены связаны между собой:**

- Телеметрия связана с датчиками через ID датчика - каждое показание привязано к конкретному датчику
- В будущем телеметрия может использоваться для автоматического управления устройствами (например, если температура упала - включить отопление)
- Каждый домен можно будет выделить в отдельный микросервис, потому что у них разная логика и данные

### **4. Проблемы монолитного решения**

- **Сложность масштабирования:** Нельзя масштабировать отдельные части системы. Если нагрузка выросла на телеметрию, приходится масштабировать весь монолит, хотя остальные части в этом не нуждаются.

- **Проблемы с развертыванием:** Любое изменение требует остановки и перезапуска всего приложения. Нельзя обновить только часть функционала.

- **Связанность компонентов:** Все части приложения находятся в одной кодовой базе, изменения в одной части могут сломать другую. Сложно разделить работу между разными командами.

- **Ограничения в выборе технологий:** Вся система на Go, нельзя использовать другие языки для разных задач, даже если они лучше подходят.

- **Единая точка отказа:** Если упадет монолит - перестанет работать вся система. Нет изоляции между доменами.

- **Сложность добавления новых устройств:** Для добавления поддержки новых типов устройств (освещение, ворота, камеры) нужно изменять монолит. Система не готова к расширению без изменения существующего кода.

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов используется **REST API** (HTTP/JSON).

**Обоснование выбора:**

1. **Простота:** REST API понятен, легко разрабатывается и тестируется
2. **Синхронное взаимодействие:** Для нашей системы управления умным домом нужны немедленные ответы (текущая температура, состояние устройств), поэтому синхронный REST подходит лучше, чем асинхронные подходы
3. **Широкая поддержка:** REST работает везде - в Go, .NET, браузерах. Легко интегрируется с любыми клиентами
4. **Swagger/OpenAPI:** Автоматическая документация и тестирование API через Swagger UI
5. **HTTP кеширование:** Можно использовать стандартные HTTP механизмы кеширования для оптимизации

В будущем для некоторых операций (например, массовый сбор телеметрии) можно добавить асинхронное взаимодействие через брокер сообщений, но для MVP REST API достаточно.

### 2. Документация API

Все микросервисы имеют Swagger UI документацию, доступную после запуска через `docker-compose up`:

**Temperature API:**
- Swagger UI: http://localhost:8081/swagger
- Эндпоинты:
  - `GET /api/temperature?location={location}` - получить температуру по локации
  - `GET /api/temperature/{id}` - получить температуру по ID датчика

**Telemetry Service:**
- Swagger UI: http://localhost:8082/swagger
- Эндпоинты:
  - `GET /api/sensors` - получить список всех датчиков
  - `GET /api/sensors/{id}` - получить датчик по ID
  - `POST /api/telemetry` - сохранить показание телеметрии
  - `GET /api/telemetry/latest?sensorId={id}` - получить последнее показание
  - `GET /api/telemetry/statistics?sensorId={id}` - получить статистику

**Device Service:**
- Swagger UI: http://localhost:8083/swagger
- Эндпоинты:
  - `GET /api/devices` - получить список всех устройств
  - `GET /api/devices/{id}` - получить устройство по ID
  - `POST /api/devices` - создать устройство
  - `PUT /api/devices/{id}` - обновить устройство
  - `DELETE /api/devices/{id}` - удалить устройство
  - `POST /api/commands` - отправить команду устройству
  - `GET /api/commands/{deviceId}` - получить команды устройства

**Go Monolith (API Gateway):**
- Базовый URL: http://localhost:8080
- Интегрированные эндпоинты:
  - `GET /api/v1/sensors` - проксирует запросы к Telemetry Service
  - `GET /api/v1/sensors/temperature/{location}` - получает температуру через Temperature API

Для тестирования доступна Postman коллекция: `apps/smarthome-api.postman_collection.json`

### 3. Асинхронное взаимодействие (To-Be)

Для будущего масштабирования системы планируется добавить асинхронное взаимодействие через **RabbitMQ** или **Kafka**.

**Зачем нужно:**

- Если сервис упал, сообщения не теряются
- Легко масштабировать под нагрузку

Вам нужно:

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081
